# ImHamster 产品设计草案

> 状态：讨论稿。记录产品目标与能力通道方向，不代表所有 Bridge 能力已经实现，也不替代后续接口规格。

## 1. 产品目标

ImHamster 是运行在 Haminn 上的 Android 通用屏幕助手。用户通过桌面悬浮球描述目标，助手尽可能利用 Android 和 Haminn 提供的能力完成任务；当没有更直接、可靠的通道时，再观察屏幕并用触摸、滑动和文字输入操作。

目标是提升普通 APK 权限范围内的手机操作覆盖率，而不是承诺可以不受限制地控制所有设备功能。Android 权限、用户授权、设备厂商差异、目标应用开放程度和系统安全边界都会限制可完成的操作。

## 2. 操作通道

执行时按目标选择最合适的通道；优先考虑可靠性、语义明确性和可验证性，再考虑速度。建议的优先顺序如下：

1. **Haminn 原生能力**：直接调用已经有明确 Bridge 合同的系统能力，例如位置、传感器、网络、相机、通知和屏幕交互。需要时先检查设备支持与授权状态。
2. **目标应用提供的入口**：在应用支持时使用 Android Intent、快捷方式、深链或公开集成入口，直接打开目标应用或功能。每个应用支持范围不同，失败时应回退。
3. **无障碍语义操作**：读取有限的控件树，按按钮名称、输入框和节点支持的动作操作。它依赖目标应用正确暴露语义信息；当前 Haminn 尚未向普通 happ 提供完整控件树查询与节点操作接口。
4. **截图与手势兜底**：截取当前画面，由视觉模型判断下一步，再通过 Haminn 执行坐标点击、滑动、文字输入或系统导航。目标不清楚、截图无法确认状态或操作失败时，应等待、询问或停止，而不是猜测。

以上是产品方向，不要求每项任务机械地逐级尝试。若某通道明确不支持目标，直接尝试下一条合适路线；若动作结果不确定，先检查状态，不盲目重放。

### 持续观察：截图变化监听

将基于截图检测屏幕变化的能力称为**截图变化监听**（Screenshot Change Watch，简称 **SCW**）。SCW 是一种观察模式：模型描述要关注的屏幕或区域及触发规则；设备端按间隔截图并本地比较；条件满足时才通知任务并提供一张新的整屏截图，由模型判断变化含义和下一步。未触发的样本不必逐张发送给模型。

SCW 应支持：

- **观察范围**：整屏或多个归一化矩形区域；每个区域独立设置变化阈值，并用“任一区域变化”或“所有区域变化”组合条件。
- **变化判定**：设备端比较连续截图中发生明显像素变化的比例。它只判定画面是否变化，不直接解释“收到新消息”或数字从 1 变成 2；变化后的完整画面再交模型理解。
- **时间条件**：采样间隔、连续命中次数，以及可选的最近若干次命中条件，用于过滤动画、时钟和轻微渲染噪声。
- **悬浮球遮挡处理**：截取整屏前暂时隐藏 Haminn 管理的悬浮球；截图完成后立即恢复显示。恢复逻辑必须覆盖截图成功、失败或取消等结束路径，避免悬浮球意外保持隐藏。
- **监听控制**：冷却时间、最大运行时长、最大触发次数，以及可查询、停止和过期状态。
- **触发处理**：变化回调只携带监听标识、触发时间和变化区域等小型元数据；任务随后获取新整屏并调用模型。回调本身不表示后续回复、发送或其他外部动作已获授权。

截图监听只观察当时实际显示的屏幕，不能读取被遮挡、未显示或安全窗口里的画面。若设备已获用户特别授权的通知监听或目标应用事件能更直接地发现变化，可以作为另一种事件源；SCW 仍可用来获取触发后的视觉上下文。无障碍窗口事件是否足够，取决于目标应用是否发出有用事件。

### 系统显著运动触发器（Haminn Bridge）

Haminn Bridge 可增加 Android `Sensor.TYPE_SIGNIFICANT_MOTION` 的原生封装，为 happ 提供设备能力查询、监听启停与状态查询，并将系统触发事件作为 Bridge 事件交付。该事件只表示系统判定发生了显著运动，不代表“摇一摇”等特定动作；是否支持由设备硬件决定，Bridge 必须报告不支持或注册失败，不能承诺所有设备都可用。

显著运动传感器是一次性触发器：每次事件到达后系统会自动停用本次注册。Haminn 原生层应在监听仍启用时重新注册，并在没有订阅者或监听被停止时注销。多个 happ 的订阅由 Haminn 原生层汇总，避免为每个订阅分别维护系统传感器注册；注册、重注册、注销和失败状态均由宿主统一管理。

这是低功耗系统触发通道，不需要 Haminn 持续采样加速度计来判定显著运动；设备休眠时传感器也可触发并唤醒设备通知应用。监听由 Haminn 原生层持有；常驻服务与后台 Worker 启用后，事件可以交给对应 happ 的后台逻辑处理，而不依赖 happ 页面 JavaScript 存活。Worker 未运行时，Haminn 可按任务策略短暂暂存事件，待其恢复后交付。设备进程被系统结束或设备重启后，原注册不会视为永久有效；Haminn 需按其常驻服务生命周期恢复注册，并遵守 Android 后台服务启动限制。

Android 依据：[显著运动传感器](https://developer.android.com/reference/android/hardware/Sensor#TYPE_SIGNIFICANT_MOTION)、[请求触发器并在触发后重新注册](https://developer.android.com/reference/android/hardware/SensorManager#requestTriggerSensor(android.hardware.TriggerEventListener,android.hardware.Sensor))。

### 通知监听与通知动作

通知是独立于截图的系统事件源，适合发现微信、抖音等应用发布的新通知。由 Haminn 原生侧实现 Android `NotificationListenerService`，再通过受控 Bridge 将能力提供给获准的 happ。通知监听授权和发布通知权限不同：用户必须在 Android 系统的“通知使用权”设置中手动启用 Haminn；Bridge 可以查询授权状态并打开设置页，但不能代替用户授权。授权只表示系统允许 Haminn 读取通知，不代表用户已经授权某个 happ 获取或处理通知内容，因此 happ 仍应有独立的能力授权和订阅范围。

建议 Bridge 能力包括：

- **授权与连接状态**：查询系统通知访问是否已授予、监听服务是否已连接；在未授权时引导用户打开系统设置。
- **当前通知快照**：查询当前仍活动的通知；这不是通知历史，已被清除或未发布为系统通知的应用内消息不在范围内。
- **事件订阅**：按来源应用包名等条件订阅通知新增、更新、移除事件，并支持查询、停止订阅。通知由原生服务接收；若 happ 会话暂不可用，Haminn 可在受限的本地队列中短暂缓存事件，待会话可用时交付。缓存需限制数量与保留时间，并避免默认长期保存通知正文。
- **结构化通知信息**：按需提供来源应用、通知标识、发布时间、标题、正文摘要、分组及可用动作等系统实际提供的字段。应用可能只发布简短提示或隐藏预览；系统版本、用户配置、工作资料策略也会影响可见字段，因此不能承诺读取所有通知的完整敏感内容。
- **打开通知**：若通知带有打开入口，提供调用该入口的能力，尝试直接打开应用提供的目标页面，无需先模拟触摸。入口可能不存在、已失效或只打开应用主页；Android 对后台启动页面有限制，调用失败时应返回明确状态，并回退到用户可见的通知栏操作或截图手势。
- **通知动作**：查询通知实际提供的按钮动作，并按动作标识调用其系统入口；只有通知确实提供时才可用。涉及发送回复等对外产生影响的动作，仍须遵守用户明确授权要求。
- **通知管理**：在 Android 接口和设备策略允许时，提供清除或延后单条通知的操作，并返回成功、拒绝或不支持等状态；不得把“调用已受理”当成目标应用内容已打开或动作已完成。

通知到达可以先触发本地规则，再由相应的后台 Worker 判断是否需要调用模型；模型不应因任意一条通知自动获得执行回复或其他外部操作的授权。只有 Haminn 常驻服务和该 happ 的后台 Worker 都处于有效状态时，通知事件才可在后台进入 happ 自定义逻辑；否则只能按有限期限暂存，待 Worker 或 happ 会话恢复后交付。通知内容、订阅来源和处理动作都应可查看、撤销，并遵循最小化读取与留存原则。

### 语音唤醒与语音输入

语音唤醒和语音识别是两种不同能力。唤醒词检测只判断本地音频中是否出现指定短语，命中后才启动完整语音识别；它不应在待机阶段持续转写用户说话或把音频发送到网络。优先使用 Android 当前语音助手/厂商实际向 Haminn 开放、且设备报告可用的低功耗热词通道。Android 与设备可能具备 Sound Trigger 硬件架构，但这不代表普通 APK 一定能访问；可用性可能依赖设备 HAL、热词模型、系统版本和用户选择的默认语音助手。因此不能把“多数设备都有低功耗热词检测”写成产品保证。

推荐行为按设备能力区分：

1. **系统低功耗热词可用**：用户在 ImHamster 中主动开启并完成所需系统设置后，由 Haminn 原生侧启动热词检测。命中后显示唤醒反馈，再启动 Haminn 已有的语音识别流程并把识别结果交给 ImHamster。停止、暂停和当前状态应可见、可控。
2. **系统热词不可用、普通语音识别可用**：不把持续运行普通语音识别当作自动降级的唤醒方案。用户仍可点击悬浮球后主动开始语音输入；这属于按需识别，不是“Hamster”待机唤醒。
3. **两者都不可用**：不显示或禁用语音输入与唤醒入口，并说明设备能力不可用。

Android 的普通 `SpeechRecognizer` 不承诺持续识别，官方提示连续使用可能显著消耗电量和网络流量。若未来增加持续识别作为实验选项，必须由用户单独主动开启，清楚标为高耗电和可能联网，遵守麦克风前台服务与系统权限要求，提供持续可见的麦克风状态以及一键停止；它不能作为系统热词缺失时的静默或自动回退，也不能冒充低功耗唤醒能力。

唤醒能力应与语音识别分开查询和授权，例如提供独立的 `wakeword.availability/start/status/stop` 与 `wakeword.detected` 事件；具体 Bridge 命名待接口设计确认。识别能力仍使用现有 `speech.availability/start/recognizeOnce` 等接口。悬浮窗本身不代表后台 Worker 正在运行；若用户启用了 Haminn 常驻服务，则由该服务管理唤醒状态，并在允许的情况下把事件交给对应后台 Worker。唤醒后如何显示 ImHamster 会话或交付识别结果，仍要遵守 Android 后台启动限制。只有命中唤醒词后才进入后续语音识别和模型处理流程。

### SCW 的运行生命周期

当前 ImHamster 的观察雏形运行在一个活动任务内，以截图轮询。它支持 1 至 8 个区域、`any`/`all` 合并、变化阈值和 5 至 120 秒观察间隔；画面未变化时会在设备端跳过模型调用，并在 `reviewEvery` 次未变化后让模型复核。`reviewEvery` 是未变化复核次数，不是连续变化触发次数。

ImHamster 在自己的任务存储中维护观察目标、规则与生命周期，并通过通用 Bridge 请求 Haminn 执行截图采样和变化检测，例如 `screen.watch.start/status/stop` 与 `screen.watch.changed`。Haminn 管理的是底层观察资源与事件投递，不负责决定事件对应哪个 ImHamster 任务、是否调用模型或如何继续执行。启用后台 JS 运行时后，ImHamster Worker 接收事件并执行自定义处理；Worker 暂不可用时，Haminn 可按通用队列策略暂存事件，恢复后交付。常驻观察必须由用户显式启用并能清楚查看、停止和限制时长；具体截图能力仍受 Android 授权、设备状态、截图频率限制和安全窗口限制。

### Haminn 常驻服务与 HAPP 后台 JavaScript 运行时

目标是由 Haminn 宿主提供一个共享的原生后台运行底座，为多个 happ 同时托管相互隔离的后台 Worker，而不是为每个 happ 各建一个 Android 服务，也不是把各 happ 的业务任务逻辑写死在 Haminn。产品目标是：只要用户启动 Haminn、任一 happ 或悬浮球，在常驻服务未被用户关闭且 Android 允许启动的前提下，都幂等地检查并确保同一个宿主服务已启动；切换 happ 或切到其他应用时，服务继续托管仍有效的 Worker 和系统事件订阅。空闲时服务保持轻量，不运行无必要的高频循环；用户可通过统一开关停止常驻能力。

宿主服务运行期间应显示持续通知，说明 Haminn 正在提供后台运行能力，并提供查看运行状态和停止服务的入口。Android 12 及以上版本限制应用从后台启动前台服务，因此应优先在 Haminn 可见或用户明确操作时启动；若从后台启动被系统拒绝，应报告“待用户启动”而不能伪报运行。Android 仍可因系统资源、用户系统级停止、进程终止或厂商电池策略中断服务；Haminn 只恢复通用 Worker 注册和系统事件订阅，不读取或管理 ImHamster 的任务内容、人格、记忆或 Skill。ImHamster 自己持久化业务任务及检查点，并在 Worker 恢复后决定如何续跑。不得绕过用户强制停止或承诺永不退出；用户再次启动 Haminn、happ 或悬浮球时，再幂等恢复通用运行底座和仍获准的 Worker。

后台逻辑由 happ 提供独立的 Worker 脚本或模块。Haminn 为每个 happ 实例创建隔离的 JavaScript 上下文，并提供通用 Worker 启停、计时器/事件回调、资源限制和受授权的 Bridge 能力；happ 自己注册、调度并管理业务任务。Worker 可以按自己的逻辑处理屏幕截图、通知、显著运动等输入，并动态决定后续调用。Haminn 不固化某个 happ 的任务队列、模型编排、提示词、记忆检索、工具选择顺序或业务流程；这些逻辑由 happ 的 JavaScript 实现并随 happ 更新。后台 Worker 与依赖页面 DOM、窗口和用户界面的前台 happ 脚本分开；happ 需要提供适配后台环境的 Worker 入口，不能假定原页面脚本及其闭包在页面销毁后仍然存在。

对于 ImHamster，第一版采用**单任务、循环执行、可恢复、可停止**的编排模型，并完全由 ImHamster happ 的 JavaScript 拥有任务队列、调度策略、任务定义、运行状态、执行记录和恢复检查点。ImHamster Worker 负责组织模型请求、选择上下文、声明本任务可用的工具、接收工具结果并继续下一轮，直到任务完成、失败、等待用户/事件或达到限制。Haminn 仅负责托管并隔离 Worker、提供通用计时器和系统事件回调、执行 Bridge 授权检查及调用底层系统能力；通知或截图变化等事件到达时，把事件交给已注册的 Worker，由 ImHamster 决定是否启动或恢复哪个业务任务。暂停、恢复、停止和状态查询由 ImHamster 的编排器实现，宿主只提供停止或唤醒 Worker 所需的通用运行时接口。

该边界使 ImHamster 可以通过更新自己的 happ/Worker 逻辑调整编排、人格与记忆策略，而不必为每个流程改动 Haminn；Haminn 仍需实现并兼容稳定的通用后台运行时和 Bridge 合同。ImHamster 应在 happ 自有存储中，于每次外部副作用操作前持久化执行意图、操作后保存返回状态，并区分“已受理”与“已核实完成”，以支持进程中断后的恢复和去重。Android 可能延迟或终止后台任务，因此这里的“可恢复”表示在系统允许的生命周期内保存状态并尽力恢复，不承诺实时调度或永不退出。

ImHamster 在自己的存储中维护任务注册表，保存业务任务标识、任务类型、上下文策略、Worker/技能版本、启停状态、触发条件、检查点和恢复策略。Haminn 只保留运行 Worker 所必需的通用注册信息、能力授权和资源配额，不持有 ImHamster 的人格、记忆、Skill 内容或任务业务记录。Bridge 每次调用仍按对应 happ 的授权检查；后台 JS 不能直接获得任意 Android API、Shell 或其他 happ 的数据。Haminn 运行时应限制 Worker 执行时间、内存、定时频率和网络调用，并支持通用启停和崩溃隔离；具体任务并发策略、暂停/恢复语义和错误处理由 ImHamster 编排器决定。

定时器按用户期望间隔尽力调度，但不是实时系统；Android 省电、系统负载、前台服务规则和截图 API 频率限制都可能延迟或拒绝调用。更适合使用通知监听、显著运动等系统事件触发器时，不应为了统一而改成高频轮询。对于截图观察，Worker 可定义区域、间隔、阈值、连续命中、冷却时间和触发后的自定义 JS 处理；Haminn 也可以提供原生截图与区域比较原语来降低开销，但不能把业务逻辑限制为宿主预设的固定动作。

实现后台 JS 运行时前，应明确支持的 JavaScript 版本和全局对象、Worker 包的来源与更新规则、脚本隔离边界、状态持久化格式及 Android 后台恢复策略。前台 happ 关闭或页面退后台后，后台 Worker 能否继续运行以常驻服务和任务状态为准，而不是依赖 WebView 页面保持存活。

### ImHamster 编排器的上下文路由、人格与记忆/Skill

任务编排、上下文选择、人格设定、记忆经验和 Skill 均由 ImHamster happ 自己实现和存储；Haminn 不理解、不生成、不检索这些内容，只按通用 Worker 与 Bridge 合同提供运行和系统能力。ImHamster 更新 happ 时可以更新编排逻辑、人格设定和 Skill，而不需要为这些产品策略修改 Haminn。

ImHamster 应把任务上下文拆成彼此独立、按需加载的部分：

- **任务上下文**：当前目标、当次截图/输入、工具结果和执行进度；每个任务都需要。
- **人格设定**：ImHamster 的名称、自我叙事、沟通风格及稳定偏好；只在需要人格化表达或需要相关长期偏好时加入，不默认注入所有任务。
- **经验记忆**：从以往已完成或有教训的任务中提炼出的事实、有效做法和限制；根据当前任务相关性检索，不把全部历史记录塞进提示词。
- **Skill**：经验证、可复用的步骤和前置条件，作为模型可参考的程序性知识；它不同于单次任务记忆，也不应被当作免检查的固定脚本。

每个任务定义应有独立的上下文策略，例如 `persona: include|omit`、`memory: off|relevant`、`skills: off|relevant|explicit`。ImHamster 编排器根据用户目标给出默认分类，用户可以查看或覆盖：直接识图、一次性操作等任务默认不带人格和历史记忆；重复流程优先检索相关经验与 Skill；涉及个人偏好、持续协作或助手自我表达的任务才带入人格设定，并按需检索记忆。分类不确定时应采用较少上下文，或在会实质改变行为时询问用户。

上下文构建与运行逻辑如下：

1. ImHamster 创建任务与运行记录，确定触发方式、可用工具、权限范围、运行预算和上下文策略。
2. Worker 只读取策略允许的上下文：加载必要的人格设定；按标签和文本相关性检索少量记忆与 Skill，并保留来源和适用条件；再与当前任务信息一起交给模型。
3. 模型与工具按单任务循环协作。每次工具结果、截图核实和任务状态变化都写入 ImHamster 自己的执行记录；任务可暂停、恢复或停止。
4. 目标经证据核实完成后，ImHamster 可从执行记录生成一条结构化的经验候选，包含适用场景、前置条件、有效步骤、结果依据、失败边界和来源。重复出现且已核实的经验可以合并去重；经验候选可用于后续检索。
5. 只有当一套经验具备明确适用条件并经过多次成功验证，或用户明确确认时，才提升为 Skill。Skill 记录版本、适用范围和验证结果；失效或相互冲突的经验应降低优先级或标记为过期，而不是静默覆盖。

人格、记忆、经验候选和 Skill 存放在 ImHamster 自己的数据空间中，用户应能查看、编辑和删除。保存时应提炼必要信息，避免把完整截图、整段私人对话、凭证或与经验无关的个人信息长期保存。第一版可用结构化元数据、标签和全文检索控制实现复杂度；语义向量检索可在数据规模和效果证明有需要后再增加。

Android 参考：[前台服务](https://developer.android.com/develop/background-work/services/fgs)、[前台服务后台启动限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)、[应用进程生命周期](https://developer.android.com/guide/components/activities/process-lifecycle)。

## 3. Bridge 设计方向

- **按能力建模**：使用有明确语义的接口，例如 `device.location.getCurrent`、`apps.launch`、`ui.snapshot`、`ui.perform`、`interaction.capture` 和 `interaction.tap`；不设计接收任意文本的通用 Shell 执行接口。
- **能力可发现**：接口能报告设备支持情况、所需权限、当前授权状态和可用动作，让助手在规划前知道哪些通道可用。
- **控件树有边界**：若增加控件树接口，只返回当前任务所需、数量受限的可见节点信息，例如短期节点引用、角色、可见文字、位置和支持动作。节点引用应绑定快照并短期有效；目标变化后要求重新取快照。
- **观察事件有边界**：SCW 在设备端先做低成本比较，只在触发时提升为整屏模型分析；变化区域和时间条件应可配置，监听任务应可查询、停止并有生命周期上限。
- **通知事件有边界**：通知监听由 Haminn 原生服务接收，通过 happ 级授权、来源过滤、有限队列和明确的订阅生命周期交付；读取通知与打开通知、调用通知动作是不同能力，分别报告结果。打开优先调用通知自带入口，无法调用时才回退到屏幕操作。
- **系统传感器触发器有边界**：显著运动由 Haminn 原生层统一注册、重注册和注销；Bridge 报告设备支持与运行状态，并向有效订阅交付事件。一次性触发、设备差异和后台会话不可用时的交付边界必须明确。
- **后台运行时与 happ 编排分层**：Haminn 维护共享常驻服务，为各 happ 托管隔离的后台 JS Worker、通用计时器、系统事件回调和受控 Bridge 能力；每个 happ 自己维护业务任务队列、调度策略、上下文策略、人格、记忆、Skill、任务状态和执行逻辑。Haminn 不参与 ImHamster 的任务或上下文决策。不得把任意 happ 页面 JS 当作天然可后台运行，也不得允许 Worker 越过本 happ 的授权和资源配额。
- **结果状态清晰**：区分成功、已受理但未核实、需要用户授权、不支持、目标已变化和执行失败。系统接受动作不等于用户目标已经完成。
- **跨通道可回退**：保留当前截图、目标和已确认进度；直接 API 或语义操作不可用时，能转为截图和手势。重要操作执行后重新观察，并据此报告结果。

## 4. 用户授权与安全边界

- 需要 Android 系统权限或 Haminn happ 授权的能力，应在调用前说明并取得对应授权。
- 热词监听必须由用户明确开启，遵守麦克风权限和前台服务要求，持续显示监听状态并提供随时停止的入口；待机检测仅在设备端运行，不默认保存或上传唤醒前音频。
- 读取其他应用通知需要用户在 Android 设置中单独授予 Haminn“通知使用权”；Haminn 不能静默开启。通知正文可能包含私人信息，happ 订阅应限定来源与字段，并允许用户随时撤销。
- 通知自带的打开入口或动作可能切换应用、发送内容或改变状态。仅检测到通知不构成执行这些动作的授权；调用外部动作前仍要有与动作相符的用户授权。
- 截图或指令发送给外部模型前，应清楚告知用户接收方和可能包含的屏幕信息。
- 发送、发布、删除、购买、授权等有外部影响的操作，必须满足用户明确授权和目标、内容可核实等条件；结果不确定时不得重复执行。
- 普通 APK 没有任意 Shell 或 root 权限。设备管理器、系统签名应用或 root 设备属于特殊部署条件，不作为默认产品能力承诺。

## 5. 当前基础与待演进项

当前 ImHamster 已有悬浮球指令入口、模型连接检查、截图识别、逐步屏幕操作与截图复核，也已有活动任务内的 SCW 原型；当前截图流程尚未实现截图前隐藏悬浮球、截图后恢复。该原型尚未提供独立的监听生命周期接口、连续变化次数条件或原生后台事件队列。Haminn 当前已有点击、滑动、焦点文字输入、截图、有限系统导航、原始传感器订阅和系统语音识别 Bridge；原始传感器订阅只在前台页面会话内有效，当前尚未向 Bridge 暴露显著运动触发器。Haminn 当前也尚无共享的常驻后台任务服务或 HAPP 后台 JavaScript Worker；页面离开前台时，当前语音识别与页面传感器订阅会被停止。ImHamster 当前也尚未实现可恢复的后台任务编排器、上下文路由、人格设定、经验记忆库或 Skill 生命周期管理；本节描述的是待开发目标。语音识别不等于热词唤醒，当前源码尚无常驻热词检测服务。Haminn 也尚未接入面向 happ 的其他应用通知监听、通知自带入口打开或通知动作调用能力。截图与指令的外发需用户同意，完成状态应由后续画面证据确认。

后续值得评估的方向：目标应用启动入口、受限控件树快照与节点动作，以及把 Haminn 已有的系统能力更好地交给 ImHamster 规划使用。每一项都应先明确 Android 授权要求、不同设备的可用性和失败后的回退方式，再决定是否实现。
